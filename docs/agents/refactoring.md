# Refactoring

## Goal

将复杂度收束在边界和深模块中：调用者只表达业务数据流，不承担底层机制、资源交换或生命周期细节。

## Design rules

- 先辨认数据流、状态转换、资源所有权和生命周期；将隐式转换收束为具名类型与操作。
- 按变化原因划分模块。协调者负责编排；机制、领域计算和资源管理各自封装。
- 在外部边界校验前置条件，并将已验证的事实编码为类型；边界以内直接依赖该事实。
- 构造完成的对象必须可用。将必要初始化纳入构造过程，避免需要额外调用才能成立的半成品状态。
- 从已稳定存在的重复中提炼抽象。抽象应减少调用方需要理解的细节，并保持最小接口。
- 让输入模型、类型和底层声明保持同源；用类型关联它们，消除可漂移的重复配置。
- 新结构替代旧结构后，删除旧路径、无用参数、无用资源和无效兼容逻辑。
- 每个资源的创建者负责其释放；初始化期临时资源在完成职责后立即释放。
- 私有属性使用无前缀的领域名（如 `material`），由 `private` 表达可见性。

## Change discipline

- 一个提交只表达一个可描述、可验证的结构变化。
- 重构中发现的行为回归以独立的小改动恢复，并保留行为等价性。
- 完成前运行与改动相关的项目检查；以 `package.json` 中的脚本和现有配置为准。

## Review questions

- 调用方是否少了解了一项实现细节？
- 状态转换、资源所有权和释放责任是否明确？
- 是否消除了半初始化或非法状态？
- 前置条件是否仅在边界验证，并由类型向内传递？
- 抽象是否来自稳定重复，且接口是否只暴露必要能力？
- 替代结构后，旧实现是否已完整移除？
